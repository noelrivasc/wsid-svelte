Code layout & conventions

Each concern has a single predictable home. Routes are thin glue.

Tree

src/
  lib/
    schemas/       Zod schemas + inferred types — the contract
    test_data/     Fixtures matching the schemas (tests, stories, seeds)
    store/         Persistence: db, schema, migrations, one repository per entity
    engine/        Pure domain logic (no IO, no clocks, no random)
    auth/          better-auth instance (server-only)
    utils/         config, mailer, small helpers
    components/    UI, grouped by feature subfolder
    app.css        Tailwind entry + @theme tokens (shared with Storybook)
  routes/          Thin glue: load → reduce → render
  cli/             Admin CLI entrypoint (bundled to build/cli.mjs)
  hooks.server.ts  Resolves session, forwards to better-auth handler

What goes where

  • schemas/ — every domain shape defined once. Imported by store, engine, components, test_data.
  • test_data/ — realistic fixtures that satisfy the schemas. Never imported by production code paths.
  • store/ — one repository file per entity (decisionRepository.ts, userRepository.ts, …). The rest of the app calls named functions (loadX, createX, appendY), never raw SQL. Migrations under store/migrations/ plus a static registry in store/migrations.bundled.ts.
  • engine/ — pure functions. Deterministic: no Date.now(), no Math.random(), no IO. IDs and timestamps passed in. See event sourcing.
  • utils/config.* — the only place that reads env. Everything else imports typed values. See env.
  • components/ — presentational + small interactive components, grouped by feature (factors/, user/, …). Stories and component tests live next to the component. Naming: <Entity><Role><Action?> (e.g. FactorForm, FactorFormEdit, UserEmailFormLogin) — entity first keeps related files adjacent.
  • routes/ — load data through the store, transform via the engine, hand to components. Logic that grows here belongs in engine/ or store/.
  • cli/ — citty subcommands. Imports from $lib/utils/config.runtime (not config) because SvelteKit's $env isn't available outside the server bundle.

Rules of thumb

  • Schemas are the contract — change shapes in schemas/ first.
  • The engine never imports from store/ — keep it IO-free.
  • The store never imports from engine/ — persistence stays decoupled from domain rules. (Importing schemas is fine; both layers share that contract.)
  • Routes never touch store/db directly — they go through a repository.
  • Config is read once, at the edge. No scattered process.env reads.
  • Test data lives in one shared place (test_data/, alongside schemas/), not scattered next to the tests that consume it.

Why this works

New code has an obvious home, so the tree stays shallow and predictable. Pure engine + thin routes means most logic is testable without a browser or a database. Swapping storage or UI framework touches one folder.
