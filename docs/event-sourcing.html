Event sourcing

A Decision is derived state. The source of truth is its ordered log of Actions.

Data model

  • src/lib/schemas/ — Zod schemas and inferred types for Decision, Factor, Scenario, DecisionMetadata.
  • src/lib/schemas/actions.ts — discriminated union of every Action type (metadata/edit, factor/{add,edit,delete}, scenario/{add,edit,delete}, scenarioFactorValue/set), each carrying a version.

Reducer

  • src/lib/engine/reducer.ts — reduce(state, action) and replay(actions).
  • Pure: no IO, no Date.now(), no random. IDs and timestamps come in via the action payload.
  • emptyDecision is the initial state.

Storage

  • src/lib/store/db.ts + schema.ts — SQLite via Kysely. Tables: decisions (id, title) and actions (decision_id, seq, type, version, payload, created_at).
  • src/lib/store/decisionRepository.ts:
    • loadDecision(id) — reads actions ordered by seq, validates each with actionSchema, runs replay.
    • createDecision(...) — inserts the decisions row + first metadata/edit action in a transaction.
    • appendAction(...) — appends the next-seq action, mirrors title to decisions.title on metadata/edit, retries on PK conflict (bounded by APPEND_ACTION_MAX_RETRIES).

Flow

UI → build Action → appendAction (persist) → on next load, loadDecision replays the log into current state.

Walkthrough

A short story showing the log → reducer → state cycle. Payload shapes are abbreviated for readability; the real ones are in src/lib/schemas/.

1. User creates a decision

createDecision('d1', 'Where to live?') inserts the decisions row and appends the first action in a single transaction. The log now has one entry; replaying it from emptyDecision gives the initial state. 

// Log
[
  { type: 'metadata/edit', version: 1,
    payload: { title: 'Where to live?', description: '' } },
]

// replay(log)
{ metadata: { title: 'Where to live?', description: '' },
  factors: [], scenarios: [], scenarioFactorValues: {} }

2. User edits metadata

The UI hands an Action to appendAction('d1', …). Persistence writes the action at the next seq and mirrors the new title onto the decisions row (that mirroring is the one denormalisation in the store — it keeps the listings page fast). 

// New action appended
{ type: 'metadata/edit', version: 1,
  payload: { title: 'Where to live?', description: 'Compare SF vs NYC.' } }

// replay(log) — metadata replaced wholesale
{ metadata: { title: 'Where to live?', description: 'Compare SF vs NYC.' },
  factors: [], scenarios: [], scenarioFactorValues: {} }

3. User adds a factor

The route generates an id (UUID) and a timestamp before calling the reducer or the store — the engine never invents either. The action goes into the log; factors grows by one on replay. 

// Appended
{ type: 'factor/add', version: 1,
  payload: { id: 'f-cost', name: 'Cost of living', weight: 3 } }

// replay(log).factors
[ { id: 'f-cost', name: 'Cost of living', weight: 3 } ]

4. User adds a scenario and sets its value for the factor

Two more actions. Note how scenarioFactorValue/set references the prior scenarioId and factorId — the reducer just slots the value into a nested map. 

// Appended
{ type: 'scenario/add', version: 1, payload: { id: 's-sf', name: 'San Francisco' } }
{ type: 'scenarioFactorValue/set', version: 1,
  payload: { scenarioId: 's-sf', factorId: 'f-cost', value: 2 } }

// replay(log) — final state
{ metadata: { title: 'Where to live?', description: 'Compare SF vs NYC.' },
  factors:   [ { id: 'f-cost', name: 'Cost of living', weight: 3 } ],
  scenarios: [ { id: 's-sf',  name: 'San Francisco' } ],
  scenarioFactorValues: { 's-sf': { 'f-cost': 2 } } }

5. User deletes the factor

factor/delete removes the factor and every dependent value across all scenarios — that fan-out is the reducer's job, not the route's. The log keeps the history (the add and the delete both stay); the derived state simply no longer contains the factor. 

// Appended
{ type: 'factor/delete', version: 1, payload: { id: 'f-cost' } }

// replay(log) — factor gone, value purged
{ metadata: { title: 'Where to live?', description: 'Compare SF vs NYC.' },
  factors:   [],
  scenarios: [ { id: 's-sf', name: 'San Francisco' } ],
  scenarioFactorValues: { 's-sf': {} } }

What this buys you

  • Time travel for free. Slice the log at any prefix and replay to see prior state.
  • Auditability. Every change is a typed, versioned action with a timestamp — no UPDATE statements to reconstruct.
  • Pure reducer. Testing the engine needs no DB and no browser — feed it actions, assert on state.
  • Schema migration is cheap. Old action payloads can keep their old version; the reducer handles each version explicitly.

Versioning actions

Every action type carries an explicit version. When an action's payload shape needs to change, bump the version and teach the reducer to accept both shapes. Old log entries replay unchanged.
