Auth

Passwordless email + magic links via better-auth. Same SQLite file as the app; sessions are server-stored and revocable.

Flow (login & register)

Both routes share the same magic-link path; they differ only at the entry step.

sequenceDiagram participant U as User participant R as Route participant A as better-auth participant M as Mailer participant DB as SQLite alt POST /users/login U->>R: email R->>DB: getUserByEmail Note over R: only proceed if user exists else POST /users/register U->>R: email Note over R: always proceed (create-on-first-use) end R->>A: signInMagicLink A->>M: sendEmail(link+token) M-->>U: email with /confirm?token U->>R: GET /confirm?token (form, token not consumed) U->>R: POST /confirm (token) R->>A: magicLinkVerify A->>DB: consume token, create session A-->>U: Set-Cookie session R-->>U: 303 → /
  1. POST /users/login — validate email with Zod; if the user exists, call auth.api.signInMagicLink. Always respond with the same neutral message.
  2. POST /users/register — same shape, but skips the existence check and always calls signInMagicLink; better-auth creates the account on first verify.
  3. The magic-link callback (in $lib/auth) builds a URL pointing at /users/login/confirm?token=… and emails it via the mailer.
  4. GET /users/login/confirm — renders a form with the token in a hidden field. Does not consume the token. This defeats email prefetchers and corporate URL scanners.
  5. POST /users/login/confirm — calls auth.api.magicLinkVerify, which consumes the token (single-use), mints a session, and sets the cookie via the sveltekitCookies plugin. Then redirects to / or a same-origin redirectTo.

Session

  • Opaque session cookie (httpOnly, secure in prod, path=/). Source of truth is the session row in SQLite.
  • expiresIn: 7 days. updateAge: 1 day — refreshes the row on activity at most once per day to limit writes.
  • Single-use magic tokens; expiresIn: 1 hour.

Asymmetry: login vs register

/users/login checks getUserByEmail first and only sends the link if the user exists. /users/register always sends (relying on better-auth's create-on-first-use). The two routes return identical neutral copy, but a careful observer could distinguish them by timing or by which route they hit. This is a deliberate UX choice — the surface still doesn't leak existence within a single route.

Mailer

src/lib/utils/mailer.ts is a thin nodemailer wrapper exposing one sendEmail({ to, subject, text, html }). Config (host/port/user/pass/from) flows from env vars. Locally it points at mailpit — see Docker setup.

Protecting a route

// any +page.server.ts
export const load = async ({ locals }) => {
  if (!locals.user) throw redirect(303, '/users/login');
  return { user: locals.user };
};

Schema

better-auth's tables (user, session, account, verification) live in the same SQLite file as domain tables. They're created by the initial migration. Don't reach into them from app code except via userRepository.ts; let better-auth own writes.
