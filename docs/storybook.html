Storybook

Component sandbox at :6006. Stories double as smoke tests via the Vitest addon.

Run

pnpm storybook        # dev server on :6006
pnpm build-storybook  # static build

Config

  • .storybook/main.ts — framework @storybook/sveltekit, globs ../src/**/*.stories.@(js|ts|svelte), addons: svelte-csf, vitest, a11y, docs, chromatic.
  • .storybook/preview.ts — imports ../src/lib/app.css so Tailwind + @theme tokens apply inside stories.

Story format

Use .stories.svelte via @storybook/addon-svelte-csf. One defineMeta, then one or more <Story> blocks. Co-locate with the component. 

<script module lang="ts">
  import { defineMeta } from '@storybook/addon-svelte-csf';
  import { fn } from 'storybook/test';
  import FactorsList from './FactorsList.svelte';
  import { sampleFactors } from '$lib/test_data';

  const { Story } = defineMeta({
    title: 'Components/Factors/FactorsList',
    component: FactorsList,
    tags: ['autodocs'],
    args: { factors: sampleFactors, onAdd: fn(), onEdit: fn(), onDelete: fn() },
  });
</script>

<Story name="Default" />
<Story name="Empty" args={{ factors: [], onAdd: fn(), onEdit: fn(), onDelete: fn() }} />

Making components render in both contexts

SvelteKit and Storybook are two separate runtimes with different bundlers and entry points. A component that works in one but breaks in the other is almost always relying on something only one of them provides. The patterns below keep both happy.

1. Shared CSS, single source

Both contexts import src/lib/app.css — SvelteKit via src/routes/+layout.svelte, Storybook via .storybook/preview.ts. The Tailwind @theme tokens (and the body background rule in @layer base) live there once. Don't duplicate styles into app.html or Storybook decorators — both contexts must consume the same file or the theming silently diverges.

2. Props in, callbacks out

Components receive data through $props() and announce events through callback props (onAdd, onEdit, …). No direct imports from $lib/store/*, no SvelteKit form actions, no $page reads. In Storybook, callbacks are stubbed with fn() from storybook/test; in routes, they're wired to real handlers. Same component, both contexts.

3. Fixtures from $lib/test_data/

Stories pass realistic data that satisfies the Zod schemas (e.g. sampleFactors, singleFactor). Same fixtures are reused by component tests and the seed script. Never import production data sources into a story.

4. Avoid SvelteKit-only modules in components

Storybook does not provide $app/*, $env/*, or any of the +page.server.ts machinery. If a component needs the current URL or env values, accept them as props from the route. The component stays portable; the route does the wiring.

5. Zod validation at the prop boundary

For components with a non-trivial prop shape, validate $props() with the component's Zod schema (see TestBox.svelte): success path renders, failure renders a role="alert" panel listing issues. Storybook can then have an InvalidProps story (cast to any to bypass the compile-time check) that exercises the runtime guard.

Stories as tests

The @storybook/addon-vitest addon auto-runs every *.stories.svelte through Vitest as a smoke test (mounts the story, asserts no render error or a11y violation per parameters.a11y.test). This runs as part of pnpm test alongside the explicit component specs.

Result: a passing story is also a passing render test, with no extra file. Reserve explicit *.svelte.spec.ts for behavioural assertions (interactions, error UI, branch coverage) — see testing.

Naming & placement

  • One .stories.svelte per component, sitting next to it.
  • Story title: Components/<Feature>/<ComponentName> (e.g. Components/Factors/FactorsList). Mirrors the directory layout so the sidebar tree matches the file tree.
  • Story names describe state: Default, Empty, SingleFactor, InvalidProps. Not "happy path" / "edge case 1".
