DB & storage

SQLite via Kysely + better-sqlite3. One file on disk, one repository per entity, migrations bundled at build time.

Where it lives

  • Path comes from DATABASE_PATH (see env), defaulting to data/wsid.db.
  • Dev: a host file under data/ (gitignored). Delete to start fresh.
  • Docker/prod: a named volume mounted at the container path. See Docker setup.

How the DB is created

src/lib/store/db.ts wires it up: createSqlite ensures the parent dir exists, opens the file (WAL, synchronous=NORMAL, foreign_keys=ON), and createDb wraps it in a Kysely instance typed by schema.ts. getConnection() is the lazy singleton used by repositories.

Schema is defined by migrations — there is no CREATE TABLE at startup. A first run is just "open the file, then migrate."

Migrations

  • Source files: src/lib/store/migrations/YYYY-MM-DD-<name>.ts with up / down.
  • Registry: src/lib/store/migrations.bundled.ts — manual map, key MUST match the filename stem. Bundled at build so the runtime image doesn't need source files on disk.
  • Runner: src/lib/store/migrator.ts, driven through the CLI.

Running them

CommandWhat
pnpm migrateApply pending migrations against the host DB (tsx).
pnpm migrate:dockerSame, but runs the bundled CLI inside the running app container.
pnpm cli migrate:status / :downInspect or roll back. :docker variants exist via pnpm cli:docker.

The container entrypoint also runs migrate on boot, so prod deploys self-apply. See CLI for the full command list.

Repositories

One file per entity under src/lib/store/ (e.g. decisionRepository.ts, userRepository.ts). They expose named functions (loadX, createX, appendY) and own all SQL/Kysely calls. Routes and the engine never touch db.ts or write SQL directly.

Import rules

  • engine → store: forbidden. Engine is pure; storage stays out.
  • store → engine: forbidden. Persistence shouldn't know domain rules.
  • both → schemas: fine; schemas/ is the shared contract.
  • routes → store: only via a repository, never store/db directly.
